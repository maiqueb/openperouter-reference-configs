= Configuring the external router

[role="_abstract"]
Configure an FRR-based router that peers with the cluster nodes over BGP,
terminates the VXLAN tunnels, and provides a VRF so that external clients can
reach the workloads. The router represents the provider edge or top-of-rack
switch in a production EVPN fabric.

.Prerequisites

* A Linux host or virtual machine with `podman` and privileges to create
  VRF, bridge, and VXLAN interfaces in a container.
* Two network attachments for the router container: one on the cluster
  underlay subnet and one on an isolated external client subnet.
* The FRR configuration files from `linux-bridge/external-router/frrconfigs/`.
* Connectivity from the underlay attachment to the node underlay addresses.

.Procedure

. Build the external router image. The build context must contain
`network-setup.sh`, so build from the `external-router` directory:
+
[source,terminal]
----
$ podman build -t frr-router linux-bridge/external-router
----

. Create a container network on the cluster underlay. The router needs an
address that is reachable from the node underlay interfaces:
+
[source,terminal]
----
$ podman network create \
    --driver macvlan \
    --opt parent=<underlay-parent-interface> \
    --subnet 192.168.10.0/24 \
    --ip-range 192.168.10.128/25 \
    --disable-dns \
    net1-ex
----
+
The `--ip-range` reserves the lower half of the subnet for cluster nodes and
the upper half for containers.

. Create an isolated network for the external client:
+
[source,terminal]
----
$ podman network create \
    --driver macvlan \
    --subnet 192.169.1.0/24 \
    --ip-range 192.169.1.128/25 \
    --gateway 192.169.1.1 \
    ext
----

. Start the router on the underlay network and mount the FRR configuration:
+
[source,terminal]
----
$ podman run -d --name frr --privileged --ulimit core=-1 \
    --volume "$PWD/linux-bridge/external-router/frrconfigs":/etc/frr \
    --network net1-ex \
    frr-router
----
+
The `network-setup.sh` entry point creates the VTEP loopback address
`100.64.0.1/32`, the `red` VRF with table 1100, the L3VNI bridge and VXLAN
interface (`br100`, `vni100`), and the L2VNI bridge and VXLAN interface
(`br110`, `vni110`). It also assigns `192.170.1.100/24` to `br110` so that the
router can respond on the stretched workload subnet.

. Connect the router to the external client network and assign the gateway
address:
+
[source,terminal]
----
$ podman network connect --ip 192.169.1.1 ext frr
----
+
The external client network is placed in the `red` VRF by the entry point
script, so traffic from an external client is routed through EVPN.

. Confirm the BGP and EVPN configuration in
`linux-bridge/external-router/frrconfigs/frr.conf`. The relevant sections are:
+
[source,frr]
----
vrf red
 vni 100
exit-vrf

router bgp 64512 vrf red
 address-family ipv4 unicast
  redistribute connected
 exit-address-family
 address-family l2vpn evpn
  advertise ipv4 unicast
  advertise ipv6 unicast
 exit-address-family
exit

router bgp 64512
 no bgp ebgp-requires-policy
 no bgp default ipv4-unicast
 neighbor ocp-nodes peer-group
 neighbor ocp-nodes remote-as 64514
 bgp listen range 192.168.10.0/24 peer-group ocp-nodes
 address-family l2vpn evpn
  neighbor ocp-nodes activate
  neighbor ocp-nodes allowas-in origin
  advertise-all-vni
  advertise-svi-ip
 exit-address-family
exit
----
+
The `bgp listen range` statement accepts dynamic BGP peers from the underlay
subnet. This is convenient in a lab, but it accepts a session from any device
in that range. `allowas-in origin` lets the router accept routes that contain
its own AS number in the AS path, which is useful when the cluster and the
router are in the same EVPN domain.

. If your underlay or external client subnet differs from the reference
values, update the network detection in `network-setup.sh`, the
`bgp listen range`, and the `network` statements in `frr.conf` before you
start the container. For the dedicated bridge example, the underlay is
`10.200.0.0/16` and the router address is `10.200.11.8`.

.Verification

. Confirm that the BGP session to every cluster node is established. It can
take a few seconds after the first `Underlay` resource is reconciled:
+
[source,terminal]
----
$ podman exec frr vtysh -c 'show bgp summary'
$ podman exec frr vtysh -c 'show bgp l2vpn evpn summary'
----
+
Each node underlay address must appear with state `Established` or with a
non-zero prefix count.

. Confirm that the router knows the L3VNI and L2VNI:
+
[source,terminal]
----
$ podman exec frr vtysh -c 'show evpn vni'
----
+
The output lists VNI 100 as `L3` and VNI 110 as `L2`, both in VRF `red`.

. Confirm that the router can reach the workload subnet:
+
[source,terminal]
----
$ podman exec frr ping -I br110 -c 3 192.170.1.3
----
+
Replace the address with the address of a workload that you have created.

[WARNING]
====
A `bgp listen range` session has no authentication. In a production fabric,
use a BGP password through a secret, enable TTL security on the neighbor, and
restrict the accepted peer range with an access list or with explicit
neighbor statements. OpenPERouter `Neighbor` resources support
`passwordSecret`, `holdTimeSeconds`, and `bfd` settings for the cluster side.
====
