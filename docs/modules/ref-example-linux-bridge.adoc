= Complete example: Linux bridge

[role="_abstract"]
The following manifests implement the Linux bridge model from `linux-bridge/`:
a kernel bridge created by Kubernetes NMState, an EVPN L3VNI and L2VNI bound
to that bridge, a `bridge` NAD for KubeVirt, and two virtual machines with
static addresses.

The NNCP, NAD, and virtual machine manifests are copied as-is after replacing
placeholders. The Underlay and VNI manifests are converted from the legacy
`openpe.openperouter.github.io/v1alpha1` API. The external router pieces are
included because this path has checked-in results.

== Node network configuration

[source,yaml]
----
apiVersion: nmstate.io/v1
kind: NodeNetworkConfigurationPolicy
metadata:
  name: linux-bridge-perouter-vni-110
spec:
  nodeSelector:
    node-role.kubernetes.io/worker: ""
  desiredState:
    interfaces:
      - name: brvni110
        type: linux-bridge
        state: up
        ipv4:
          enabled: false
          dhcp: false
        bridge:
          options:
            stp:
              enabled: false
----

== Underlay

[source,yaml]
----
apiVersion: network.openperouter.io/v1alpha1
kind: Underlay
metadata:
  name: underlay-worker0
  namespace: openperouter-system
spec:
  nodeSelector:
    matchLabels:
      kubernetes.io/hostname: <worker-node-0>
  asn: 64514
  tunnelEndpoint:
    cidrs:
      - 100.65.0.0/24
  neighbors:
    - asn: 64512
      address: 192.168.10.129
  interfaces:
    - type: CNIDevice
      cniDevice:
        type: RawConfig
        interfaceName: net1
        rawConfig:
          cniVersion: "1.0.0"
          name: macvlan-underlay
          plugins:
            - type: macvlan
              master: ens4
              mode: bridge
              ipam:
                type: static
                addresses:
                  - address: 192.168.10.100/24
---
apiVersion: network.openperouter.io/v1alpha1
kind: Underlay
metadata:
  name: underlay-worker1
  namespace: openperouter-system
spec:
  nodeSelector:
    matchLabels:
      kubernetes.io/hostname: <worker-node-1>
  asn: 64514
  tunnelEndpoint:
    cidrs:
      - 100.65.0.0/24
  neighbors:
    - asn: 64512
      address: 192.168.10.129
  interfaces:
    - type: CNIDevice
      cniDevice:
        type: RawConfig
        interfaceName: net1
        rawConfig:
          cniVersion: "1.0.0"
          name: macvlan-underlay
          plugins:
            - type: macvlan
              master: ens4
              mode: bridge
              ipam:
                type: static
                addresses:
                  - address: 192.168.10.101/24
----

The `CNIDevice` raw configuration creates the underlay device in the router
pod on top of the node interface, for example the macvlan on `ens4` shown
here. The parent interface stays in the host network namespace, so you do not
need to create a `NodeNetworkConfigurationPolicy` for it. Use an `ipvlan`
plugin when the underlay must share the MAC address of the parent, and attach
the device to an OVS internal interface when the parent is an OVS bridge.
Create one `Underlay` per node with a unique address, as described in
xref:proc-preparing-the-node-underlay_{context}[Preparing the node underlay].

== VNIs and anycast gateway

[source,yaml]
----
apiVersion: network.openperouter.io/v1alpha1
kind: L3VNI
metadata:
  name: red-100
  namespace: openperouter-system
spec:
  vrf: red
  vni: 100
---
apiVersion: network.openperouter.io/v1alpha1
kind: L2VNI
metadata:
  name: red-110
  namespace: openperouter-system
spec:
  vni: 110
  routingDomain:
    type: L3VNI
    l3vni:
      name: red-100
  gatewayIPs:
    - 192.170.1.1/24
  hostMaster:
    type: LinuxBridge
    linuxBridge:
      lifecycle: External
      name: brvni110
----

    k8s.v1.cni.cncf.io/resourceName: bridge.network.kubevirt.io/brvni110

    {
      "cniVersion": "0.3.1",

== Verification

Confirm first that NMState applied the bridge policy and that OpenPERouter
accepted the VNIs:

[source,terminal]
----
$ oc get nncp linux-bridge-perouter-vni-110 -o yaml
$ oc get nnce -l nmstate.io/policy=linux-bridge-perouter-vni-110 -o yaml
$ oc get routernodeconfigurationstatus -n openperouter-system
----

In `status.conditions` of the policy, `Available` must be `True` with reason
`SuccessfullyConfigured`, and each enactment must report `Available: True`.
Each `RouterNodeConfigurationStatus` must show `READY` as `True` and `DEGRADED`
as `False`, with an empty `status.failedResources`.

The tests check bidirectional connectivity between the two virtual machines,
between each virtual machine and the external router `br110` address
`192.170.1.100`, and between each virtual machine and the external client. To
verify the EVPN control plane directly:

[source,terminal]
----
$ oc exec -n openperouter-system <router-pod> -c frr -- \
    vtysh -c 'show evpn vni'
$ oc exec -n openperouter-system <router-pod> -c frr -- \
    vtysh -c 'show bgp l2vpn evpn route type 2'
$ podman exec frr vtysh -c 'show bgp l2vpn evpn summary'
----
