= Attaching a virtual machine to the EVPN network

[role="_abstract"]
Attach a KubeVirt virtual machine to the EVPN workload segment with a Multus
network and a bridge interface, and configure the guest address with
cloud-init. The network attachment and the MAC address rules depend on whether
you use OVN-Kubernetes localnet or a Linux bridge.

.Prerequisites

* OpenShift Virtualization is installed and a `HyperConverged` instance is
  available.
* You have created a network attachment for the chosen model:
  ** An OVN-Kubernetes localnet `ClusterUserDefinedNetwork` from the dedicated
  bridge or shared single NIC procedure.
  ** The `bridge` NAD from the Linux bridge procedure.
* For the OVN-Kubernetes localnet model, the `ClusterUserDefinedNetwork`
  `namespaceSelector` matches the virtual machine namespace. OVN-Kubernetes
  creates a `NetworkAttachmentDefinition` with the same name in that
  namespace.
* You have a container disk image and, optionally, an SSH key secret.
* The virtual machines can be scheduled on nodes that run the OpenPERouter
  router pod.

.Procedure

. Create the virtual machine with a Multus network and a bridge interface.
The following skeleton applies to both models:
+
[source,yaml]
----
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-1
  namespace: <namespace>
spec:
  runStrategy: Always
  template:
    spec:
      domain:
        devices:
          interfaces:
            - bridge: {}
              name: evpn
          disks:
            - name: containerdisk
              disk:
                bus: virtio
            - name: cloudinitdisk
              disk:
                bus: virtio
      networks:
        - multus:
            networkName: <nad-name>
          name: evpn
      volumes:
        - name: containerdisk
          containerDisk:
            image: <containerdisk-image>
        - name: cloudinitdisk
          cloudInitNoCloud:
            networkData: |
              version: 2
              ethernets:
                eth0:
                  addresses:
                    - 192.170.1.3/24
                  gateway4: 192.170.1.1
----

. For an OVN-Kubernetes localnet attachment, set `networkName` to the
`NetworkAttachmentDefinition` that OVN-Kubernetes created for the
`ClusterUserDefinedNetwork`, and use only the gateway in the guest
configuration:
+
[source,yaml]
----
      networks:
        - multus:
            networkName: <namespace>/evpn
          name: evpn
----
+
MAC spoof checking is always enabled for the KubeVirt localnet path. Do not
configure a guest MAC address that differs from the MAC that OVN-Kubernetes
assigns to the pod interface. For the same reason, do not enable promiscuous
mode in the guest. If you need a fixed MAC address, use the Linux bridge
model instead.

. For a Linux bridge attachment, set `networkName` to the `bridge` NAD, set a
fixed MAC address on the interface, and match that MAC address in the
cloud-init network data:
+
[source,yaml]
----
      domain:
        devices:
          interfaces:
            - bridge: {}
              macAddress: 02:79:38:33:33:33
              model: virtio
              name: evpn
              state: up
      networks:
        - multus:
            networkName: <namespace>/evpn-l2vni-110
          name: evpn
      volumes:
        - name: cloudinitdisk
          cloudInitNoCloud:
            networkData: |
              version: 2
              ethernets:
                id0:
                  match:
                    macaddress: "02:79:38:33:33:33"
                  addresses:
                    - 192.170.1.3/24
                  gateway4: 192.170.1.1
----
+
The `macspoofchk: false` setting in the Linux bridge NAD allows the guest to
keep this MAC address.

. If the virtual machine also has the default pod network with masquerade
binding, add a return route for the external client network through the EVPN
gateway:
+
[source,yaml]
----
                id0:
                  match:
                    macaddress: "02:79:38:33:33:33"
                  addresses:
                    - 192.170.1.3/24
                  gateway4: 192.170.1.1
                  routes:
                    - to: <external-client-network>
                      via: 192.170.1.1
----
+
Without this route, reply traffic to the external client can follow the
default route on the pod network instead of the EVPN interface. If the EVPN
interface is the only interface, or if it is the default route, the return
route is not required. Replace `<external-client-network>` with the CIDR of the
network behind the external router.

. If the cluster has more than one node, schedule the virtual machines on
different nodes so that the path uses VXLAN. On a single-node cluster, the
workload stays on the local bridge. Use `nodeSelector` or pod anti-affinity:
+
[source,yaml]
----
      nodeSelector:
        kubernetes.io/hostname: <worker-node-1>
----
+
or:
+
[source,yaml]
----
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchExpressions:
                  - key: app
                    operator: In
                    values:
                      - evpn-workload
              topologyKey: kubernetes.io/hostname
----

. Apply the virtual machine and wait for it to start:
+
[source,terminal]
----
$ oc apply -n <namespace> -f vm.yaml
$ oc wait vm/vm-1 -n <namespace> \
    --for=condition=Ready --timeout=10m
$ oc wait vmi/vm-1 -n <namespace> \
    --for=condition=AgentConnected --timeout=10m
----

.Verification

. Confirm that the guest received the address:
+
[source,terminal]
----
$ virtctl ssh -n <namespace> fedora@vm/vm-1 -- \
    ip addr show
----
+
The EVPN interface must have the static address and the gateway from the
cloud-init data.

. If you scheduled a peer virtual machine on another node, confirm
connectivity to it:
+
[source,terminal]
----
$ virtctl ssh -n <namespace> fedora@vm/vm-1 -- \
    ping -c 3 192.170.1.5
----

. Confirm connectivity to the external router and, if configured, the
external client:
+
[source,terminal]
----
$ virtctl ssh -n <namespace> fedora@vm/vm-1 -- \
    ping -c 3 <external-router-ip>
$ virtctl ssh -n <namespace> fedora@vm/vm-1 -- \
    ping -c 3 <external-client-ip>
----
+
Replace `<external-router-ip>` with the external router address on the workload
segment and `<external-client-ip>` with the address of a client behind the
external fabric.

. Confirm that the external EVPN/BGP fabric contains a Type-2 route with the
virtual machine MAC address and its IP address binding.
+
If you use the containerized FRR router from the reference lab, you can check
this from the lab host:
+
[source,terminal]
----
$ podman exec frr vtysh -c 'show bgp l2vpn evpn route type 2'
----

[NOTE]
====
The `capabilities.mac` and `runtimeConfig.mac` settings belong to the
`Underlay` `CNIDevice` configuration. They select the MAC address of the
underlay macvlan that OpenPERouter uses for BGP; they do not set the MAC
address of a virtual machine interface.
====
