= Complete example: shared single NIC

[role="_abstract"]
The following manifests implement the shared single NIC model from
`localnet/br-ex/`: OVN-Kubernetes keeps `br-ex` for the default cluster
network, OpenPERouter uses a macvlan on `br-ex` for the underlay, and a
separate OVS bridge carries the EVPN workload segment.

These manifests already use the current
`network.openperouter.io/v1alpha1` API. They are copied as-is except for the
namespace, which the example normalizes to `openperouter-system`, and the
node names, which the example marks as placeholders. The repository files use
`openshift-openperouter`.

== Secondary bridge and OVN-Kubernetes mapping

[source,yaml]
----
apiVersion: nmstate.io/v1
kind: NodeNetworkConfigurationPolicy
metadata:
  name: localnet-dedicated-bridge
spec:
  nodeSelector:
    node-role.kubernetes.io/worker: ""
  desiredState:
    interfaces:
      - name: ovsbr1
        type: ovs-interface
        state: up
        ipv4:
          enabled: false
        ipv6:
          enabled: false
      - name: ovsbr1
        type: ovs-bridge
        state: up
        bridge:
          allow-extra-patch-ports: true
          options:
            stp: false
          port:
            - name: ovsbr1
    ovn:
      bridge-mappings:
        - bridge: ovsbr1
          localnet: datanet
          state: present
----

`br-ex` is not modified. It keeps the physical uplink and the OVN-Kubernetes
patch port that carry the default cluster network.

== Optional host macvlan

The repository also contains a policy that creates a host macvlan named
`macvlan0` on `br-ex`:

[source,yaml]
----
apiVersion: nmstate.io/v1
kind: NodeNetworkConfigurationPolicy
metadata:
  name: macvlan-underlay
spec:
  nodeSelector:
    node-role.kubernetes.io/worker: ""
  desiredState:
    interfaces:
      - name: macvlan0
        type: mac-vlan
        state: up
        mac-vlan:
          base-iface: br-ex
          mode: bridge
        ipv4:
          enabled: false
        ipv6:
          enabled: false
----

This policy is optional for the current configuration. The `Underlay`
`CNIDevice` creates the operative underlay interface, `net1`, and obtains its
address through DHCP. If you apply the host macvlan policy, `macvlan0` remains
unused by OpenPERouter; inspect `net1` when you verify the underlay.

== Underlays, VNIs, and anycast gateway

[source,yaml]
----
apiVersion: network.openperouter.io/v1alpha1
kind: L3VNI
metadata:
  name: red
  namespace: openperouter-system
spec:
  vni: 100
  vrf: red
---
apiVersion: network.openperouter.io/v1alpha1
kind: L2VNI
metadata:
  name: layer2
  namespace: openperouter-system
spec:
  hostMaster:
    type: OVSBridge
    ovsBridge:
      lifecycle: External
      name: ovsbr1
  gatewayIPs:
    - 192.170.1.1/24
  vni: 110
  routingDomain:
    type: L3VNI
    l3vni:
      name: red
---
apiVersion: network.openperouter.io/v1alpha1
kind: Underlay
metadata:
  name: underlay-worker0
  namespace: openperouter-system
spec:
  nodeSelector:
    matchLabels:
      kubernetes.io/hostname: <worker-node-0>
  asn: 64514
  tunnelEndpoint:
    cidrs:
      - 100.65.0.0/24
  neighbors:
    - asn: 64512
      address: 192.168.122.15
  interfaces:
    - type: CNIDevice
      cniDevice:
        type: RawConfig
        interfaceName: net1
        rawConfig:
          cniVersion: "1.0.0"
          name: macvlan-underlay
          plugins:
            - type: macvlan
              master: br-ex
              mode: bridge
              capabilities:
                mac: true
              ipam:
                type: dhcp
        runtimeConfig:
          mac: "aa:bb:cc:00:00:01"
---
apiVersion: network.openperouter.io/v1alpha1
kind: Underlay
metadata:
  name: underlay-worker1
  namespace: openperouter-system
spec:
  nodeSelector:
    matchLabels:
      kubernetes.io/hostname: <worker-node-1>
  asn: 64514
  tunnelEndpoint:
    cidrs:
      - 100.65.0.0/24
  neighbors:
    - asn: 64512
      address: 192.168.122.15
  interfaces:
    - type: CNIDevice
      cniDevice:
        type: RawConfig
        interfaceName: net1
        rawConfig:
          cniVersion: "1.0.0"
          name: macvlan-underlay
          plugins:
            - type: macvlan
              master: br-ex
              mode: bridge
              capabilities:
                mac: true
              ipam:
                type: dhcp
        runtimeConfig:
          mac: "aa:bb:cc:00:00:aa"
----

Each node needs a unique `runtimeConfig.mac` so that the external router and
the DHCP server can distinguish the underlay interfaces.

== Localnet network attachment

[source,yaml]
----
apiVersion: k8s.ovn.org/v1
kind: ClusterUserDefinedNetwork
metadata:
  name: evpn
spec:
  namespaceSelector:
    matchLabels:
      kubernetes.io/metadata.name: evpn-localnet-test
  network:
    topology: Localnet
    localnet:
      role: Secondary
      physicalNetworkName: datanet
      ipam:
        mode: Disabled
----

The OVN-Kubernetes controller creates a `NetworkAttachmentDefinition` named
`evpn` in the `evpn-localnet-test` namespace. `ipam.mode: Disabled` leaves IP
configuration to the workloads, which use the static addresses in their
Multus annotations and the anycast gateway that OpenPERouter provides.

== VLAN trunk adaptation

If you want to expose additional VLANs of the same trunk as direct
OVN-Kubernetes secondary networks, use the existing `physnet:br-ex` mapping
and create a `ClusterUserDefinedNetwork` with the `Localnet` topology. Use
`localnet.vlan` to set the access VLAN:

[source,yaml]
----
apiVersion: k8s.ovn.org/v1
kind: ClusterUserDefinedNetwork
metadata:
  name: evpn-vlan-200
spec:
  namespaceSelector:
    matchLabels:
      kubernetes.io/metadata.name: <namespace>
  network:
    topology: Localnet
    localnet:
      role: Secondary
      physicalNetworkName: physnet
      vlan:
        mode: Access
        access:
          id: 200
      ipam:
        mode: Disabled
----

`ipam.mode: Disabled` leaves addressing to the workloads. To let
OVN-Kubernetes assign addresses, omit `ipam` and set `localnet.subnets` to
the VLAN subnet. To use a DHCP server on the VLAN, set `ipam.mode: DHCP` and
omit `subnets`.

These VLAN networks are direct Layer 2 networks. They are not stretched by
OpenPERouter. If a VLAN must also be part of the EVPN fabric, create a
dedicated bridge with an access port for that VLAN and an L2VNI for that
bridge. v0.3.0 has no VLAN tag field in the L2VNI.

== Verification

[source,terminal]
----
$ oc debug node/<worker-node> -- chroot /host \
    ovs-vsctl get open . external_ids:ovn-bridge-mappings
$ oc debug node/<worker-node> -- chroot /host ovs-vsctl show
$ oc exec -n openperouter-system <router-pod> -c frr -- ip addr show net1
$ oc exec -n openperouter-system <router-pod> -c frr -- \
    vtysh -c 'show bgp l2vpn evpn summary'
----

[NOTE]
====
The checked-in results under `localnet/br-ex/results/` predate the switch to
the `CNIDevice` underlay. They show `macvlan0` and a BGP neighbor at
`192.168.122.201`. The current manifest uses `net1` and the neighbor
`192.168.122.15`. Use the manifests for configuration and the results only as
an illustration of the expected bridge mapping, VNI state, and EVPN routes.
====

== Teardown

[source,terminal]
----
$ oc delete namespace evpn-localnet-test
$ oc delete clusteruserdefinednetwork evpn
$ oc delete l2vni layer2 l3vni red -n openperouter-system
$ oc delete underlay underlay-worker0 underlay-worker1 -n openperouter-system
$ oc delete nncp localnet-dedicated-bridge
$ oc delete nncp macvlan-underlay <1>
----
<1> Delete this policy only if you applied the optional host macvlan policy.

The `ClusterUserDefinedNetwork` is cluster-scoped. Deleting the namespace
removes only the `NetworkAttachmentDefinition` that OVN-Kubernetes generated,
so delete the `ClusterUserDefinedNetwork` as well. If you created the VLAN
trunk network, also delete `clusteruserdefinednetwork evpn-vlan-200`.

Deleting the NNCP removes `ovsbr1` and the bridge mapping. It does not remove
`br-ex` or the default cluster network.
