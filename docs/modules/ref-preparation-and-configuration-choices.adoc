= Preparation and configuration choices

[role="_abstract"]
Before you install the operators or create any OpenPERouter resources, decide
which attachment model fits your cluster, reserve the addresses and VNI
identifiers that the examples use, and check whether the manifests in this
repository use the API version that your operator provides.

== What the examples assume

The procedures and examples in this assembly assume the following
environment. The procedures create most of these resources; the list is here
so that you can confirm the assumptions before you start.

* An OpenShift Container Platform cluster with cluster-admin access and the
  `oc` CLI.
* OVN-Kubernetes as the cluster network provider, with Multus available for
  secondary networks.
* At least two worker nodes on the same underlay Layer 2 segment.
* A dedicated NIC, a bond, a shared NIC, or a bridge that can carry the
  underlay and the EVPN workload segment. The underlay uses a macvlan or
  ipvlan device on top of that interface or bridge. The shared NIC model
  additionally requires that OVN-Kubernetes already use `br-ex`.
* The Kubernetes NMState Operator installed and a `NMState` instance created.
* OpenPERouter v0.3.0 installed in the `openperouter-system` namespace.
* For virtual machines, OpenShift Virtualization installed and a
  `HyperConverged` instance created.
* An external router that runs FRR and has one interface on the underlay
  network, one interface on the external client network, and VXLAN and BGP
  connectivity to the cluster nodes.

[NOTE]
====
The checked-in `linux-bridge/` and `localnet/dedicated-bridge/` manifests use
the older `openpe.openperouter.github.io/v1alpha1` API. They do not apply
unchanged to an OpenPERouter v0.3.0 operator. The examples in this assembly are
the converted equivalents. `localnet/br-ex/03-openperouter-logical-infra.yaml`
and `localnet/br-ex/migration-networks/*` already use the current
`network.openperouter.io/v1alpha1` API and need only a namespace substitution.
====

== Choosing an attachment model

The following table compares the models that this assembly documents. The
choice affects the NAD type, the bridge owner, and whether pods or virtual
machines can use the attachment.

|Bridge owner
|OVN-Kubernetes, through a bridge mapping
|OVN-Kubernetes for `br-ex`; OpenPERouter L2VNI on a separate `ovsbr1`
|Kernel, through a `NodeNetworkConfigurationPolicy`

|Workload types
|Pods and virtual machines
|Pods and virtual machines
|Virtual machines with the reference NAD; pods need a different NAD

|NAD type
|`ovn-k8s-cni-overlay`, `topology: localnet`
|`ovn-k8s-cni-overlay`, `topology: localnet`
|`bridge`, with the KubeVirt bridge resource annotation

|Dedicated NIC or bond
|Recommended
|Not required; the node has a single NIC or bond
|Required for the OpenPERouter underlay in the reference configuration

|VLAN trunking
|One localnet network per VLAN; no trunk mode
|One localnet network per VLAN; no trunk mode
|One L2VNI per bridge; no VLAN tag field in the L2VNI

|OVN-Kubernetes network policy
|Yes
|Yes for the localnet network
|No; OVN-Kubernetes does not manage the kernel bridge

|MAC spoof checking
|Always on for the KubeVirt localnet path
|Always on for the KubeVirt localnet path
|Disabled in the reference NAD with `macspoofchk: false`

|Promiscuous mode
|Not supported
|Not supported
|Not required by the reference configuration

|Live migration within the cluster
|Supported
|Supported
|Supported

|Choose this model when
|You want OVN-Kubernetes to own the segment and you can dedicate a bridge
|You have one NIC or bond and want to keep the default cluster network on
`br-ex`
|You want a plain kernel bridge and KubeVirt bridge binding independent of
OVN-Kubernetes
|===

The shared single NIC model has two variants. In the repository pattern,
VXLAN stretches the secondary Layer 2 segment over the underlay, so the
physical uplink does not need a VLAN for that segment. In the VLAN trunk
variant, which is adapted from the OpenShift Container Platform documentation,
one VLAN carries the default cluster network and the remaining VLANs are
exposed as separate OVN-Kubernetes localnet secondary networks. Those VLANs
are not stretched by OpenPERouter unless you also create one bridge and one
L2VNI per VLAN.

== Mapping the legacy API to v0.3.0

Use the following table when you convert a manifest from the older
`openpe.openperouter.github.io/v1alpha1` API.

[cols="2,2,4"]
|===
|Legacy field |v0.3.0 field |Notes

|`apiVersion: openpe.openperouter.github.io/v1alpha1`
|`apiVersion: network.openperouter.io/v1alpha1`
|The group changed. The version remains `v1alpha1`.

|`spec.nics`
|`spec.interfaces`
|Recreate each interface as an object with `type: CNIDevice` and a
`cniDevice` raw CNI configuration that creates a macvlan or ipvlan device on a
node interface or bridge.

|`spec.hostmaster`
|`spec.hostMaster`
|Field names are case-sensitive.

|`hostmaster.type: ovs-bridge`
|`hostMaster.type: OVSBridge`
|The nested field is `ovsBridge`.

|`hostmaster.type: linux-bridge`
|`hostMaster.type: LinuxBridge`
|The nested field is `linuxBridge`.

|No equivalent
|`hostMaster.ovsBridge.lifecycle` or `hostMaster.linuxBridge.lifecycle`
|Required in v0.3.0. Use `External` when a `NodeNetworkConfigurationPolicy`
or OVN-Kubernetes owns the bridge.

|`spec.l2gatewayips`
|`spec.gatewayIPs`
|A list of CIDR strings.

|L2VNI `spec.vrf`
|`spec.routingDomain.l3vni.name`
|The value is the *name of the L3VNI object*, not the VRF name. For example,
`red-100` is an L3VNI object whose `spec.vrf` is `red`.
|===

The correct nesting for an OVS bridge is:

[source,yaml]
----
hostMaster:
  type: OVSBridge
  ovsBridge:
    lifecycle: External
    name: ovsbr1
----

For a Linux bridge, use `type: LinuxBridge` and the `linuxBridge` field with
the same `lifecycle` and `name` keys.

== Design choices

VNI layout:: Reserve one L3VNI for the tenant VRF and one L2VNI for each
Layer 2 segment. VNI identifiers must be unique within the EVPN fabric, not
only within the cluster. The examples use VNI 100 for the L3VNI and VNI 110
for the workload L2VNI.

VRF name:: Use one VRF per tenant and use the same name on every node. The
VRF name is independent of the L3VNI object name. In the Linux bridge example,
the L3VNI object is `red-100` and its VRF is `red`.

Gateway address:: Use an anycast gateway address that is outside the range
that DHCP or static allocation assigns to workloads. The examples use the
first address in the subnet, `192.170.1.1`.

MTU:: VXLAN adds 50 bytes of encapsulation. The underlay must carry the
encapsulated frame, and the workload interface must use an MTU that fits
inside the tunnel. The repository results show an underlay MTU of 1500 and an
L2VNI SVI MTU of 1450. The exact value depends on your underlay and on any
additional encapsulation. Verify it with `ping -M do -s <size>` rather than
assuming a fixed offset.

Underlay addressing:: Static addresses are easier to troubleshoot and are used
by the dedicated bridge and Linux bridge examples. DHCP is used by the shared
single NIC example, where the underlay interface is a macvlan created through
a CNI device. DHCP requires `capabilities.mac` and a stable `runtimeConfig.mac`
so that the external router can identify the peer.

Bond mode:: A kernel bond in `active-backup` mode can host a macvlan for the
underlay and is the simplest choice when the bond is dedicated to OpenPERouter.
An OVS bond in `balance-slb` mode is an alternative for the shared model, but
an OVS bond is not a kernel network device, so a macvlan cannot be created
directly on it. Attach the macvlan to an OVS internal interface instead. Do
not combine the two bond variants in the same bridge.
