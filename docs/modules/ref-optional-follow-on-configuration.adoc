= Optional follow-on configuration

[role="_abstract"]
After the basic EVPN secondary network works, you can add inter-subnet
routing, more Layer 2 segments, dual-stack addressing, OpenPERouter-managed
bridges, and fabric tuning. The features in this section are optional and have
different support requirements.

== Inter-subnet and external routing

The L3VNI provides the VRF that connects the workload subnet to the external
fabric. On the external router, the VRF address family redistributes the
connected subnet, and the EVPN address family advertises the VNI:

[source,frr]
----
router bgp 64512 vrf red
 address-family ipv4 unicast
  redistribute connected
 exit-address-family
 address-family l2vpn evpn
  advertise ipv4 unicast
  advertise ipv6 unicast
 exit-address-family
exit

router bgp 64512
 address-family l2vpn evpn
  advertise-all-vni
  advertise-svi-ip
 exit-address-family
exit
----

`advertise-svi-ip` makes the router advertise the gateway IP address in EVPN.
The external client needs a route back to the workload subnet through the
external router. On the cluster side, the L3VNI installs the external routes
in the tenant VRF.

If a virtual machine has both the default pod network and the EVPN network,
add an explicit return route through the EVPN gateway, as shown in the Linux
bridge example. Otherwise, reply traffic can follow the default route on the
pod network.

== Additional Layer 2 segments and VLANs

In v0.3.0, create one bridge and one L2VNI for each Layer 2 segment. For
example, to add a second segment on `ovsbr2` with VNI 120:

[source,yaml]
----
apiVersion: network.openperouter.io/v1alpha1
kind: L2VNI
metadata:
  name: layer3
  namespace: openperouter-system
spec:
  hostMaster:
    type: OVSBridge
    ovsBridge:
      lifecycle: External
      name: ovsbr2
  gatewayIPs:
    - 192.171.1.1/24
  vni: 120
  routingDomain:
    type: L3VNI
    l3vni:
      name: red
----

Create `ovsbr2` and a second OVN-Kubernetes bridge mapping, for example
`datanet2:ovsbr2`, and create a second localnet NAD with
`physicalNetworkName: datanet2`. If the new segment belongs to a different
tenant, create a separate L3VNI and VRF and reference that L3VNI in the
`routingDomain`.

For a VLAN on a shared trunk, OVN-Kubernetes applies the tag with `vlanID` in
a NAD or with `layer2.vlan` in a CUDN. OpenPERouter v0.3.0 has no VLAN tag or
trunk field in the L2VNI. A dedicated `L2Trunk` resource and an `L2VNI`
`trunk` field were added after v0.3.0; they are not available with the
installation described in this assembly.

== Dual-stack and IPv6

An L2VNI can carry more than one gateway address. Add an IPv6 gateway
alongside the IPv4 gateway:

[source,yaml]
----
spec:
  gatewayIPs:
    - 192.170.1.1/24
    - fd00:170:1::1/64
----

The underlay and the external router must also support the address family.
The reference environment uses kernel 5.18 or later for full IPv6 EVPN
support.

== OpenPERouter-managed bridges

Set `lifecycle: Managed` when OpenPERouter should create the bridge instead of
attaching to an existing one. Omit `name`; OpenPERouter names the bridge after
the VNI:

[source,yaml]
----
apiVersion: network.openperouter.io/v1alpha1
kind: L2VNI
metadata:
  name: migration-net
  namespace: openperouter-system
spec:
  hostMaster:
    type: LinuxBridge
    linuxBridge:
      lifecycle: Managed
  gatewayIPs:
    - 192.170.10.1/24
  vni: 666
  routingDomain:
    type: L3VNI
    l3vni:
      name: rouge
----

This example is based on
`localnet/br-ex/migration-networks/l2vni.yaml` and creates the bridge
`br-hs-666`. The same file creates the `rouge` L3VNI, with VNI 777 and VRF
`rouge`, that the `routingDomain` references.

A managed bridge is convenient for a network that no other component owns. Do
not use `Managed` for a bridge that OVN-Kubernetes or a
`NodeNetworkConfigurationPolicy` owns.

== EVPN and top-of-rack tuning

The following settings matter when the workload segment crosses more than one
EVPN domain, for example between two clusters that are connected by
top-of-rack switches:

Route targets:: FRR derives import route targets from the local ASN and the
VNI, for example `64514:100`. Setting an explicit `route-target import`
replaces the derived list rather than adding to it. In a multi-ASN fabric,
list every ASN whose routes the VRF must import, including the local ASN.

Router MAC uniqueness:: Each top-of-rack switch or router should use a unique
router MAC on its L3VNI SVI. FRR silently drops incoming Type-5 routes whose
router MAC matches the local router MAC, as a loop-prevention measure. If two
routers share a router MAC, the Type-5 routes from one of them do not appear
in the other's EVPN table. Assign a unique address, for example:

[source,terminal]
----
$ ip link set br100 address aa:bb:cc:00:00:64
----

MRAI:: Keep the Minimum Route Advertisement Interval at zero on every eBGP
hop if you need fast reconvergence after a MAC move. The investigation in
`docs/cclm-migration-analysis.md` measured sub-second EVPN route propagation
across three eBGP hops with MRAI set to zero.

== Cross-cluster live migration

KubeVirt can live-migrate a virtual machine between clusters when both
clusters have the same workload L2VNI and the EVPN fabric stretches that
segment. The repository contains an example migration network under
`localnet/br-ex/migration-networks/`, and the analysis in
`docs/cclm-migration-analysis.md` describes the observed packet loss and the
fabric settings that affect it.

Cross-cluster migration is outside the scope of this assembly and is not
documented as a procedure here. Treat the migration-network manifests as a
starting point and validate the fabric, route targets, router MAC addresses,
and KubeVirt migration settings for your environment.

== External router hardening

The reference router accepts dynamic BGP peers from an entire underlay
subnet:

[source,frr]
----
bgp listen range 192.168.10.0/24 peer-group ocp-nodes
----

Before you use this configuration outside a lab, restrict the accepted peers
and authenticate the sessions:

* Use explicit `neighbor <address>` statements instead of a dynamic listen
  range when the node set is stable.
* Configure a BGP password and a TTL security check on the neighbor.
* Apply an access list or a prefix list to the accepted routes.
* Limit the underlay subnet to the addresses that the nodes actually use.

On the cluster side, an OpenPERouter `Neighbor` supports `passwordSecret`,
`holdTimeSeconds`, `keepaliveTimeSeconds`, `connectTimeSeconds`, `bfd`, and
`addressFamilies`.
